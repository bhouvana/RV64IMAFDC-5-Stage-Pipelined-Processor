# Roadmap

This backlog exists because "turn this into a comprehensive research platform" isn't a single task — it's a multi-year program. Treating it as one undifferentiated pile of work is how projects end up with ten half-finished subsystems and none of them trustworthy. Every item below is scoped to be independently reviewable, verifiable, and mergeable. Items are grouped by the phase they belong to (see [ARCHITECTURE.md](ARCHITECTURE.md) §15 for phase definitions) and ordered by dependency, not by phase number — several Phase-2/3 items block everything in Phases 4–10.

**This file covers what's actually scheduled now.** For where the project goes after the current RV32IMAF work (Phase A-E, plus the in-progress second wave — MMU → caches → dual-issue) closes out, see [ROADMAP_VISION.md](ROADMAP_VISION.md) — a user-confirmed, 10-generation long-range plan (RV64 → OS support/MMU → advanced memory → multicore → out-of-order → vector → security → FPGA SoC → a fully configurable research platform). That file also has the reconciliation notes for how its generation numbering relates to this file's phase numbers and the ADRs' own Phase A-E/F-H letters — read it before assuming any naming lines up.

Each item that touches RTL or changes observable behavior should get a short ADR (`docs/adr/NNNN-title.md`) before implementation: **Problem, Background, Alternatives considered, Tradeoffs, Chosen solution, Expected impact, Validation strategy.** Purely additive documentation/tooling work doesn't need one.

## Sequencing logic

```
P0 fixes (correctness/portability) ─┬─→ Verification harness ─┬─→ Visualization
                                     │                          ├─→ Benchmarking
Code-quality pass (defs, dedup) ────┘                          └─→ Research-platform parameterization
                                                                        │
ISA completion (P1) ────────────────────────────────────────────────→ Extensions (RV32M/CSR/caches/...)
                                                                        │
                                                                        └─→ FPGA bring-up
```

Verification has to exist before visualization or benchmarking mean anything (you can't visualize or benchmark execution you haven't proven correct). ISA completion should land before layering RV32M/CSR/privilege on top of a base that's still missing `jalr`/`lui`/`auipc`/byte loads.

Three more bugs surfaced *while building the verification harness* (P0-adjacent, found and fixed the same way): `ALU.v`'s broken `sra`, a register-file same-cycle write/read race (`docs/adr/0002-...`), and store data bypassing forwarding (`docs/adr/0003-...`). ## Phase 5 — ISA/architectural extensions

Ordered by how much they build on each other:
1. **ISA completeness first**: ✅ Done (`docs/adr/0005-isa-completeness.md`). `jalr`, `lui`, `auipc`, `bltu`/`bgeu`, byte/halfword loads-stores all implemented and verified (4 new directed tests, 16 checks). Found and fixed a real bug along the way (`docs/adr/0004`: `slt`/`blt`/`bge`/`ble`/`bgt` were comparing unsigned). RV32I base is now complete except `fence`/`ecall`/`ebreak`/CSR (see item 3).
2. **RV32M** (mul/div) — ✅ Done, including the real multi-cycle divider. First version (`docs/adr/0006-rv32m.md`) used Verilog's native `/`/`%` (single-cycle); `docs/adr/0009-multicycle-divider.md` replaced `div`/`divu`/`rem`/`remu` with a genuine 32-cycle iterative unit (`design/Divider.v`) plus a real pipeline interlock (PC/IF-ID freeze, ID/EX hold, EX/MEM bubble-then-latch) -- the project's first multi-cycle-execute mechanism. `mul`/`mulh`/`mulhsu`/`mulhu` stay single-cycle (a defensible simplification even for real hardware, unlike division). Also widened `funct7` from 1 bit to the full 7-bit field (a prerequisite RV32M's opcode reuse needed, and now removes the same wall for any future R-type extension).
3. **CSR + machine mode + exceptions** — ✅ Done (`docs/adr/0011-csr-and-exceptions.md`). New `design/CSR.v` register file (`mstatus`/`mtvec`/`mscratch`/`mepc`/`mcause`); `Control.v`/`ImmGen.v` decode `csrrw`/`csrrs`/`csrrc`(`+i`)/`ecall`/`ebreak`/`mret`; illegal instructions (both a fully unrecognized opcode and a recognized opcode with an unrecognized funct7/funct3) now trap instead of silently no-opping. Reused the `docs/adr/0009` redirect/squash machinery directly — exceptions and `mret` are just two more `unconditional_redirect` sources. Real interrupts were explicitly out of scope at the time (no hardware interrupt source existed yet) — see item 5 below, `docs/adr/0020`.
4. **RV32F (single-precision floating point)** — ✅ Done (`docs/adr/0019-f-extension.md`). Full extension including `fdiv.s`/`fsqrt.s` and the `fmadd.s`/`fmsub.s`/`fnmsub.s`/`fnmadd.s` family, with full float register forwarding from the start (both chosen as the more ambitious option over a reduced first pass). New `design/FRegister.v`/`FALU.v`/`FDivider.v`/`FSqrt.v`/`FMADDUnit.v`/`FForward.v`, `CSR.v` extended with live `fflags`/`frm`. Ten independently-verified steps (C1–C10); found and fixed four real bugs along the way, including one (`fma_op_regde`'s opcode bit slice) that had silently shipped through three prior phase steps before an independent Python reference model caught it. `sim/tools/asm.py`/`iss.py`/`disasm.py`/`random_gen.py` all extended with real F-extension support; 675 constrained-random programs cross-checked against the independent model with zero mismatches.
5. **SoC integration: a real bus, UART, timer, and real hardware interrupts** — ✅ Done (`docs/adr/0020-soc-integration.md`). A classic Wishbone-style bus (`design/WbDecoder.v`, `design/RamWishboneAdapter.v` wrapping the existing `DataMemoryBRAM.v` unmodified) now sits between the LSU and every memory-mapped device; a cycle-accurate `design/Uart.v` (real bit-shifted 8N1 framing) and a CLINT-style `design/Timer.v` (`mtime`/`mtimecmp`) are the first two peripherals. `CSR.v` gained real `mie`/`mip` and `mcause`'s interrupt bit; `riscvpipeline.v` gained the actual asynchronous-interrupt redirect path — independent of whatever instruction is in EX (unlike every existing exception), correctly computing `mepc` as "the instruction that would have executed next" rather than the exception path's own faulting-instruction PC, with spec-mandated external-over-timer priority. `sim/tools/random_gen.py`/`iss.py`/`run_random_tests.py` gained an opt-in interrupt-injection mode built on the insight that the RTL's real hardware timing and the ISS's own externally-scheduled firing point don't need to agree on the exact instruction boundary, given an architecturally-inert injected handler — sidestepping real cycle-accurate co-simulation entirely. Twelve independently-verified steps (D1–D12); found and fixed real bugs at nearly every layer, including a genuine `CSR.v` correctness bug (an unrelated CSR write silently dropped whenever an interrupt happened to fire the same cycle) that only became possible once the interrupt redirect made `trap_taken` independent of EX's occupant — not caught until a 100-seed random sweep, well past this step's own directed tests.
6. **Branch prediction** — ✅ Done (`docs/adr/0021-branch-prediction.md`, Phase E of the redesign, the last phase). A per-PC 2-bit-saturating-counter branch-history table (`design/Bht.v`) plus a branch-target buffer (`design/Btb.v`), covering conditional branches *and* `jal`/`jalr`, selected via a new `BRANCH_PREDICTOR` parameter (`PREDICTOR_STATIC`=0, today's exact "always guess not-taken" behavior, bit-exact default; `PREDICTOR_DYNAMIC_BHT_BTB`=1). `riscvpipeline.v`'s redirect logic changed from "squash on every taken branch/jump" to "squash only on an actual misprediction" — a correctly-predicted branch now costs zero bubble cycles, down from today's fixed 2-cycle penalty; a genuine misprediction still costs exactly what it always did. `sim/tools/bench_runner.py --compare-predictors` quantifies the result: 11-24% fewer cycles across all three benchmark kernels. Confirmed (by research, then by running) fully transparent to `sim/tools/iss.py` and needing no analog to Phase D's interrupt-injection safety machinery, since misprediction recovery never changes architectural control flow, only its timing.
7. **MMU (Sv32)** — ✅ Done (`docs/adr/0022-mmu-sv32.md`, Phase F of the second wave). Full Sv32: M/S/U privilege modes, 2-level page tables, a unified TLB (`design/Tlb.v`), a page-table walker sharing the LSU's bus port via a mux (`design/Ptw.v`), and real page faults (instruction/load/store) with privilege-aware trap delegation (`mideleg`/`medeleg`). Nine independently-verified steps (F1-F9); found and fixed six real bugs wiring it live (F5) — a stall-over-redirect priority bug, TLB-miss X-propagation, an uncancelled in-flight walk trusting a stale result past an intervening redirect, a bus side-band port never muxed for the walker's own reads, and forwarding-window exhaustion corrupting a stalled load/store's address and data operands — plus two more in the MMU-aware random-test generator (F7): a 12-bit immediate overflow and a random CSR op privilege-trapping into an unset handler. `sim/tools/iss.py` gained a from-scratch Sv32 walker matching the RTL bit-for-bit (flagged up front as the hardest verification-tooling task in the project's history, unlike branch prediction's zero-ISS-change case). 150/150 MMU-enabled + 60/60 non-MMU constrained-random cross-check clean. Dual-issue dropped from near-term scope entirely per the Generation 1 scope decision (`docs/ROADMAP_VISION.md`); caches followed next as Phase G (see item 8 below).
8. **Caches (I$ + D$)** — ✅ Done (`docs/adr/0023-caches.md`, Phase G). PIPT, 4-way set-associative, 4KB, 16-byte-line I-cache (`design/ICache.v`, read-only, no bus port — it privately owns its own `InstructionMemory.v`, nothing else shares it) and D-cache (`design/DCache.v`, write-back + write-allocate, Wishbone-master-shaped fill/writeback engine), selected via a new `CACHE_MODE` parameter (`CACHE_NONE`=0, today's exact direct-memory behavior, bit-exact default; `CACHE_WRITEBACK_SETASSOC`=1). `fence` gained real semantics for the first time (previously undecoded, would have trapped): it now flushes every dirty D$ line to memory through the same generalized `mem_stall` interlock a D$ miss uses. Ten independently-verified steps (G1–G10); found and fixed four real bugs wiring it live, including a subtle split-fetch/redirect duplicate-fetch bug and a deep response-latching bug in `DCache.v` only caught by address-matching the latched request against the current one rather than trusting bare FSM state. `sim/tools/bench_runner.py --compare-cache` quantifies hit/miss behavior per benchmark. Confirmed no `iss.py`/`random_gen.py` architectural changes needed beyond inserting `fence` before every test program's halt loop (a timing-only feature, same zero-ISS-change category as branch prediction) — except one real MMU/cache coherency gap the page-table-setup random generator itself needed a `fence` for, since `Ptw.v`'s raw bus reads bypass `DCache.v` by design. 150/150 MMU-enabled + 60/60 non-MMU constrained-random cross-check clean under caching, including full memory-dump comparison. Variable-latency memory followed next as Phase I (see item 9 below).
9. **Variable-latency memory** — ✅ Done (`docs/adr/0024-variable-latency-memory.md`, Phase I). Independently configurable I-side and D-side wait-state cycles (`MEM_LATENCY_I`/`MEM_LATENCY_D`, both 0 by default, bit-exact) via a new generic `design/MemoryLatencyModel.v` delay-line primitive. D-side: a single wrapper around `RamWishboneAdapter.v` shared transparently by the raw LSU, `DCache.v`'s fill/writeback engine, and `Ptw.v`'s walker, needing zero changes to any of the three. I-side: a genuinely new interlock (`InstructionMemory.v` has no handshake of its own) for `CACHE_NONE` fetch, plus a matching wait inside `ICache.v`'s own internal fill engine. Eight independently-verified steps (I1–I8); found and fixed four real bugs wiring it live, all variations on this project's own recurring "distinguish a fresh request from a repeat" bug class — a naive ack-delay design broke `Ptw.v`'s own back-to-back two-level walk, a request-delay redesign broke `DCache.v`'s multi-word burst the same way, the eventual address-tracked fix still left a one-cycle gap letting a real fetch slip past `reg1` before the artificial stall caught up (only exposed under dynamic branch prediction), and a retrigger gap in that same fix's own bookkeeping silently doubled every I-side wait's real duration. `sim/tools/bench_runner.py --compare-latency` quantifies the result: ~3-4x more cycles at `MEM_LATENCY_I=D=3` across all three benchmark kernels. Confirmed no `iss.py`/`random_gen.py` architectural changes needed (the ISS has no cycle model at all, so a wait-state RAM model is timing-only by the same reasoning as caches and branch prediction). Full cross-product constrained-random cross-check clean across every axis (`HAZARD_STRATEGY` × `PIPELINE_PROFILE` × `BRANCH_PREDICTOR` × `CACHE_MODE` × MMU × both latency axes), including the combined "everything at once" configuration.
10. **Hardware performance-monitoring CSRs** — ✅ Done (`docs/adr/0025-hpc-performance-csrs.md`, Phase J). Spec-standard `mcycle`/`minstret` (64-bit, read-write) plus `mcountinhibit` and 9 generic `mhpmcounter3`-`mhpmcounter11`/`mhpmevent3`-`mhpmevent11` pairs, each independently selecting one of 9 countable hardware events (branches/jumps retired, mispredicts, I$/D$ hits/misses, pipeline stall cycles, interrupts taken, exceptions taken) — a genuine indexed array in `CSR.v`, the first structurally-identical CSR group in that file, mirroring `Tlb.v`/`DCache.v`'s own array/`generate` idiom rather than 9 hand-unrolled registers. `design/reg2.v`/`design/reg3.v` gained a new `valid` bit (reusing `riscvpipeline.v`'s existing `id_bubble_r`) threaded through to a `!mem_stall`-gated `instret_pulse` for exact-once instruction retirement counting; `design/DCache.v` gained `access_hit`/`access_miss` output ports. Nine independently-verified steps (J1–J9); found and fixed one real bug wiring it live — a D$ read-hit double-counting itself once on returning to `S_IDLE` with a still-stale `req_read` (fixed by counting a read-hit at its own `S_HIT_RD` completion cycle instead, mirroring `docs/adr/0023`'s own G7 latched-address-match fix). Confirmed by research that the constrained-random cross-check's fixed-shape dump comparison can't see any CSR address at all, so zero `sim/tools/iss.py` changes were needed — the same "RTL-only, not ISS-modeled" category as cache-miss counters. The performance profiler (Generation 1's next item) is what will actually consume these counters; deliberately not built in this phase. Full cross-product constrained-random cross-check clean across every axis.
11. **Performance profiler** — ✅ Done (`docs/adr/0026-performance-profiler.md`, Phase K). New `sim/tools/profiler.py` (sibling to `bench_runner.py`, which stays untouched) runs every `sim/benchmarks/bench_*.s` kernel through two RTL runs each and reports IPC/CPI, branch accuracy, I$/D$ hit rate, aggregate + 9-way per-cause stall breakdown, and a static instruction-mix histogram, as both a stdout table and `--json`. Counters are read via real `csrrs` instructions the profiled program itself executes (confirmed via `AskUserQuestion` as the more-ambitious option over a simulation-only testbench tap), keeping the profiler meaningful on real FPGA hardware later. `design/CSR.v`'s `mhpmevent` widened from 4 to 5 bits (K1) to add 9 new per-cause stall events (10-18, sourced from `riscvpipeline.v`'s own already-existing `stall`/`div_stall`/`mem_stall`/`fp_stall`/`float_load_use_hazard`/`itlb_miss`/`dtlb_miss`/`icache_miss`/`imem_wait` wires — the exact terms already forming `pc_stall`'s own OR). New `sim/tb/profiler_template.v` combines `bench_template.v`'s halt-loop completion detection with `dump_regs_template.v`'s full 32-register dump. Four new directed tests (K1); found and fixed a real bug in the profiler tool itself (not the RTL): a reprogrammed counter kept counting under its old reset-default event for the few cycles its own `csrrwi` took to commit, contaminating the very first stall-cause reading — fixed by explicitly zeroing every counter right after reprogramming. 77/77 directed tests, zero-warning compile, full cross-product constrained-random cross-check clean (100/100 default, 40/40 per axis, 40/40 combined, 60/60 MMU-enabled) — plus one **pre-existing** random-test-generator gap found and confirmed unrelated to this phase (combining all 6 axes with `--interrupt both` simultaneously already failed on a clean Phase-J checkout). Formal verification (Generation 1's last remaining item) is next.
12. **Formal verification** — ✅ Done (`docs/adr/0027-formal-verification.md`, Phase L). First formal toolchain in this project (Yosys + SymbiYosys, OSS CAD Suite). 5 real, unbounded (k-induction) BMC proofs: `Register.v` (x0==0, write-first bypass), `Forward.v` (priority-encoder correctness, not just the original out-of-range invariant), `Hazard.v`/`HazardNoForward.v` (stall/flush correctness, including `docs/adr/0016`'s own historical bug restated as a proven property), and a `CSR.v` subset (trap-entry/exit MIE/MPIE/SIE/SPIE/SPP/priv_mode swap correctness). `design/reg4.v` gained `valid_regwb` (closing the loop `docs/adr/0025`'s own `valid_regde`/`valid_regem` opened) and `design/CSR.v`/`design/riscvpipeline.v` gained small formal-observability output ports (same "unconnected changes nothing" shape as `docs/adr/0012`'s `debug_x10`) — Yosys's `read_verilog` can't resolve a hierarchical peek into a submodule's internals the way `iverilog` can. A 6th proof (a whole-pipeline property: a committing register write is always from a real, non-squashed instruction) was attempted with real engineering effort — a blackboxed formal harness, dummy stand-ins for the non-synthesizable F-extension units — but hit a genuine Yosys `write_smt2` "logic loop" hard-error tracing `dtlb_miss`→`branch_taken`→`interrupt_taken`→`pc_stall`→`dtlb_miss`, very likely a structural-loop-detector false positive (this exact interaction has been extensively cross-product random-tested with zero anomalies across four prior phases) but not conclusively resolved this phase — honestly documented as a real, actionable finding rather than forced through. Zero regression: 77/77 directed tests, zero-warning compile, 80/80 fresh random cross-check. **This closes out Generation 1** (`docs/ROADMAP_VISION.md`) — RV32IMAF Research Processor v1.0 is complete; Generation 2 (RV64) is next.
13. **RV64 migration foundation** — ✅ Done (`docs/adr/0028-rv64-migration-phase-m.md`, Generation 2's own Phase M — phase-lettering continues per `docs/ROADMAP_VISION.md`'s own instruction to point new work at Generation numbering). Widens the existing RV32IMAF datapath to real XLEN=64 correctness (fixing two real sign-extension bugs in `ImmGen.v`/`DataMemoryBRAM.v`'s `lw`) and adds the full new RV64-only instruction family: `addw`/`subw`/`sllw`/`srlw`/`sraw`/`mulw`/`divw`/`divuw`/`remw`/`remuw`/`addiw`/`slliw`/`srliw`/`sraiw` (reusing OP/OP-IMM's own ALUCtl codes via a new `wordOp` signal, not new codes) and `ld`/`sd`/`lwu`. MMU stays Sv32-only, force-disabled at XLEN=64 (Generation 3's own new-design task). Eighteen independently-verified steps (M1-M18); found and fixed ten real bugs, including a `WbDecoder` address-map corruption that hung every load/store at XLEN=64 and a missing `ImmGen.v` case arm that silently zeroed every `addiw`/`slliw`/`srliw`/`sraiw` immediate. Full toolchain (`asm.py`/`disasm.py`/`iss.py`/`debugger.py`/`gen_trace.py`/`run_random_tests.py`/`random_gen.py`) gained real XLEN=64 support in lockstep, not deferred. 83/83 directed tests, zero-warning compile, 100/100 random cross-check at XLEN=32 (regression) plus 195 seeds at XLEN=64 across every axis this project's harness supports. Compliance-suite integration (riscv-arch-test) is a separate later phase.

## Phase 6 — Research platform (pluggable subsystems)

Requires CQ-1 (defs) and the parameterization cleanup noted in §12 (widths/depths as `parameter`, not literals) before "compare hazard strategies" or "compare pipeline depths" is even mechanically possible. `DataMemory`/`InstructionMemory` size parameterization is done (`docs/adr/0012`, done alongside FPGA readiness since both needed it). The architectural register file and pipeline register widths are now also parameterized (`XLEN`/`NUM_REGS`, `docs/adr/0015-xlen-and-regcount-parameterization.md`) -- named, not truly variable at other values (RV32I's own encoding fixes a 32-bit instruction word and 5-bit register fields), but a single source of truth instead of scattered literals, and the prerequisite cleanup this phase's roadmap text names.

**"Compare hazard strategies" is now done** (`docs/adr/0016-swappable-hazard-strategy.md`): a new `HazardNoForward.v` (stall on every RAW hazard instead of forwarding), selected via `riscvpipeline.v`'s `HAZARD_STRATEGY` parameter (`generate`/`if` at elaboration time, so the default strategy costs nothing and needed zero changes to any existing test). `sim/tools/bench_runner.py --compare-strategies` runs the Phase 10 benchmark suite under both and reports the delta: removing forwarding costs 30-43% more cycles across all three kernels. Found and fixed a real bug along the way -- a stall from the new module could silently swallow a `jal`/`jalr`'s redirect by colliding with `PC.v`'s stall-priority-over-redirect behavior, the fourth occurrence of "a new interlock signal has to be checked against everything else that shares its consumer" (`docs/adr/0009`, `0013`, `0014`, now this).

**"Compare pipeline depths" is now partially done** (`docs/adr/0018-variable-pipeline-depth.md`): a new `PIPELINE_PROFILE` parameter on `PIPELINED`, closed and named (same honesty convention as `XLEN`/`NUM_REGS` and `HAZARD_STRATEGY`) -- `PROFILE_5STAGE` (0, default, bit-exact) and `PROFILE_6STAGE_SPLIT_FETCH` (1, a new `reg1a` IF1/IF2 relay register ahead of the existing IF/ID boundary). Deliberately the structurally cheap alternate depth: `Forward.v`/`Hazard.v`/`reg2`/`reg3`/`reg4`/the divider and MEM-stage interlocks all anchor at ID/EX/MEM/WB, none of which a fetch-side split touches. `Forward.v`/`Hazard.v` are also now generalized (`NUM_FWD_SRC`/`NUM_LOOKAHEAD` parameters, defaults reproducing today's exact behavior bit-for-bit) as infrastructure for a future deeper split, not exercised above their defaults by profile 1. `sim/tools/gen_trace.py`'s pipeline viewer explicitly refuses (clear `$fatal`, not a silent wrong trace) to trace anything but `PROFILE_5STAGE` -- its CSV schema/`viewer_template.html` are hardcoded to exactly 5 stages, a full rework is out of scope here. `sim/tools/bench_runner.py --compare-profiles` (mirroring `--compare-strategies`) quantifies the result: profile 1 costs 9-14% more cycles across all three kernels, the honest price of one extra redirect-recovery cycle through a deeper fetch pipe. Found and fixed three real bugs wiring profile 1 in (see the ADR): a PC/instruction pairing bug corrupting every PC-relative computation, a squash-to-0 bug causing a genuine infinite loop, and a duplicate-fetch bug from the first fix attempt -- the actual fix extends `reg1`'s own squash window by one cycle under this profile instead of giving `reg1a` its own squash logic.

**Splitting EX/MEM (branch-resolve-early, cache-miss stalls) remains explicitly not attempted** -- the genuinely hard half of "compare pipeline depths": hazard/forwarding logic anchored there would need a real redesign, deliberately scoped out as disproportionate risk against a fully-verified core rather than attempted as a drive-by addition. Real future work, not silently dropped.

**"Compare branch predictors" is now done** (`docs/adr/0021-branch-prediction.md`, Phase E of the redesign): a third parameter in the same swappable-subsystem family as `HAZARD_STRATEGY`/`PIPELINE_PROFILE` above -- `BRANCH_PREDICTOR` (closed, named enum; `PREDICTOR_STATIC`=0, default, bit-exact with every pre-Phase-E test/ADR/benchmark; `PREDICTOR_DYNAMIC_BHT_BTB`=1, a new `design/Bht.v`/`design/Btb.v` pair). Verified at every combination of all three axes (predictor × profile × strategy) plus every interrupt-injection mode, all clean. `sim/tools/bench_runner.py --compare-predictors` mirrors `--compare-strategies`/`--compare-profiles` exactly: 11-24% fewer cycles across all three benchmark kernels.

**Status update**: **Phase W is CLOSED** (`docs/adr/0039-amo-hazard-fix-phase-w.md`). The sp/tp park documented above turned out to be a real RTL hazard-detection bug, not an environment gap: `Hazard.v`'s load-use detector gates its stall on `memRead_regde` alone, and `Control.v` deliberately leaves `memRead`=0 for `OPCODE_AMO` — blinding that earlier, decode-stage check to an in-flight AMO's own destination register. The real kernel's own aliased `amoadd.w a3,a2,(a3)` / `bnez a3,...` hart-lottery pair let the dependent branch race ahead one cycle too early, reading `a3`'s stale pre-AMO (always-nonzero address) value and wrongly taking the "lost the lottery" path. Root cause confirmed via a real Verilator trace (new debug taps + a `+pc-trace-min=` harness flag) matched instruction-for-instruction against real upstream kernel source. One-line fix: `.la_memRead(memRead_regde | isAmo_regde)`. Confirmed fixed by re-running the identical trace: the branch is no longer taken, and the kernel now runs ~208,000 cycles further before hitting a new, later, different blocker (a real Sv39 instruction page fault during the kernel's own MMU-enable sequence) — a genuinely new frontier, not chased further this phase. Also found and fixed two pre-existing, unrelated infrastructure gaps blocking the regression suite entirely (73 testbenches missing a post-Phase-U include; a second, wrong Icarus install on this machine). **88/90 directed tests** (right toolchain) — same two pre-existing unrelated failures as unmodified `HEAD`, zero regressions from this phase's own change. No standalone directed AMO test yet (`asm.py` has no AMO mnemonic support, flagged in `docs/adr/0038` and again here) — the real kernel re-run is this phase's evidence. Real GUI boot is not a reachable goal for this core (no display hardware exists in this design at all) — confirmed with the user before starting; this phase stayed scoped to the core's own real boot progress.
